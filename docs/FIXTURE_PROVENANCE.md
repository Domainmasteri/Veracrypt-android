# Test fixture provenance

The committed `test.vc`, `fat32_test.vc`, and `exfat_test.vc` files contain no
user data. They are reproducibly generated by
`core-native/src/androidTest/assets/generate_test_container.py` with the public
password `test`, fixed salts and fixed test-only master keys. The script records
and asserts each SHA-256 digest. CI verifies the same digests before building.

These fixtures exercise the VeraCrypt version-5 header, AES-256-XTS,
PBKDF2-HMAC-SHA-512, FAT32 nested Unicode LFN traversal, a 192 KiB FAT chain,
exFAT boot/bitmap/upcase metadata, nested traversal and a fragmented exFAT file.
They are independent format implementations, not evidence that the official
VeraCrypt formatter produced the filesystem images.

Production release therefore still requires a separately maintained corpus
created with a pinned official VeraCrypt release on at least two host operating
systems. That corpus must contain FAT32 and exFAT root/nested/Unicode/empty/
large/fragmented cases, record the exact VeraCrypt version and creation command,
use public test-only passwords, and be checked by SHA-256. Real private volumes
must never be uploaded to CI. If corpus licensing prevents committing it, a
pinned digest-verified private CI artifact is acceptable; a mutable URL is not.

Cryptsetup's public `tcrypt-images.tar.xz` is useful for header algorithm
regression but explicitly says its data blocks were wiped for compression. It
does not satisfy the filesystem interoperability gate.
